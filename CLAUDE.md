# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Clashweave is a Minecraft 1.7.10 / Forge 10.13.4.1614 combat mod (Japanese-sword first, more weapons later), built on the GTNH Gradle convention plugin. The design docs and reports are written in Chinese; the README and `docs/design/executor-entry.md` are the entry points (rule priority: user review conclusions → module rules in `docs/design/modules/` → prototype spec → older proposals → original draft).

## Build and test

Gradle runs on **Java 25** (`gradle/gradle-daemon-jvm.properties`); sources compile with a real **JDK 8** toolchain (`enableModernJavaSyntax=false`), so no `var`, no switch arrows, no records. Without a git tag, set `VERSION=0.1.0-dev`.

```bash
./gradlew spotlessApply test jar     # format, all JUnit, build (Spotless + Checkstyle run in the build)
./gradlew test --tests 'com.layue13.clashweave.client.body.LocomotionTest'   # one test class
./gradlew runClient                  # dev client (coremod flag is wired in build.gradle.kts)
```

- `jar` output names embed the git hash and dirty flag (`build/libs/clashweave-<hash>-<branch>+...-dev.jar`); the plain `clashweave-0.1.0-dev-dev.jar` can be a **stale** leftover. Pick the newest `*-dev.jar` by mtime, and check a class you just changed is in it.
- Always format with `spotlessApply` before committing; CI-style checks fail on formatting.
- Tests that touch Minecraft classes (`ModelBiped`, `ModelRenderer`, …) run fine in plain JUnit; zero-allocation hot-path tests (`PoseAllocationTest`, `HotPathAllocationTest`, `MobBodiesTest`) are the performance guardrail.

## Live-game verification harness (`tools/p0`)

Fixtures are an opt-in jar, not part of the production jar. Rebuild it after editing anything under `tools/p0/java`:

```bash
JAVA_HOME='C:\Program Files\Zulu\zulu-25' VERSION=0.1.0-dev \
  ./gradlew p0LaunchFiles p0ValidationJar -I tools/p0/validation.gradle --no-configuration-cache --console=plain
```

`tools/p0/dual.py` launches a dedicated server plus two real Forge clients (P0A, P0B) behind a latency proxy and writes `build/p0/runs/<label>/` (summary.json, per-client logs and `P0A/screenshots`). Always pass `--mod-snapshot build/<mod>-dev.jar --snapshot-coremod --accept-eula` (the `-dev.jar`, not the reobf jar) and a fresh `--label`. Only one run at a time (ports 25580/25581). Useful modes: `--pose-verify <yaw>` (every combat action photographed), `--souls-view` (combo cycles), `--move-verify <yaw> --move-mode player|mobs|stance|crowd|crowdmobs|walkers` (movement layer, monsters, engaged stance walk), `--armor`, `--jvm-arg=-D...`. Verify looks from several yaws (0/45/90/135/180); a side view alone hides seams and detached limbs.

## Architecture

**Authority split.** The server is authoritative; the dedicated server must never load client classes.
- `core/` is pure logic with no Minecraft imports (scheduler, action catalog, input gate, budgets, lock/camera math). `content/` loads and validates data packs under `assets/clashweave/content/<ns>/` and builds `EffectiveRules`; client and server compare a manifest hash on handshake. `forge/` is the server side (`CombatServer`, hit sweeps, config); `network/` holds the message types; `client/` is presentation only (renderers, camera, body animation, weapon drawing). Presentation may differ between peers; rules may not.
- `coremod/` is a client-only camera hook (`CameraLoadingPlugin`, wired through the jar manifest and `runClient`).
- Baked combat tracks live in `assets/clashweave/tracks/katana.tracks.json` (deliberately **not** under `content/`, so the loader doesn't parse them and the manifest hash ignores them). They are generated by `art/katana/motion2.py` (pure Python): `python art/katana/motion2.py src/main/resources/assets/clashweave/combat/katana.json src/main/resources/assets/clashweave/tracks/katana.tracks.json`. Regenerate, run tests, never hand-edit.

**Body animation stack (client).** The whole player body, not only combat, is driven by one system; monsters of a few plain `ModelBiped` classes use the same one.
- `client/body/`: `BodyRig` (one per entity, frame-rate-independent exponential chase of 22 channels, see `Channels`), `Locomotion` (ground/swim/ride/climb/fly layers; `Gait` holds per-body character numbers; a busy arm keeps vanilla's pose), `Smoothing`.
- `client/pose/`: baked track sampling and closed-form two-bone IK (`LimbSolver`); runtime does no search.
- `PoseDriver` decides per frame whether a combat track takes the body over (weight chased by the rig; the idle ready stance keeps chest/arms/blade but lets the legs follow locomotion); `KatanaPlayerRenderer` feeds inputs and owns `CombatBiped` (skin model with elbow/knee segments, plus rigid armor models that follow the pose).
- `BipedChannels` reads vanilla's pose into rig channels and writes the smoothed result back, shared by players and monsters. `LimbSlicer` cuts any single-box limb at the joint from the model's own faces (texture re-derived per face, octagonal prism fills the bend wedge). `MobBiped` + `MobBodies` swap a monster renderer's model on `RenderLivingEvent.Pre`, only for exact classes `ModelZombie/Skeleton/Biped/ZombieVillager` (and the enderman through its own branch: only `mainModel` is swapped, the eye layer keeps the donor); anything else is left alone.
- Invariants that took debugging to find: `ModelBiped` parts are independent (not hierarchical), and vanilla's `setRotationAngles` never resets head/body pivots, arm pivot Y, leg pivot X or leg Z — one shared model draws every entity, so pivots must be restored each call. The torso must rotate **about the hips** with neck/shoulders/head riding the same rotation, or the lower torso detaches from the legs. Rotation order is Rz·Ry·Rx; Biped space is X = left, Y down, Z back. Forge event handler classes must be `public`.

## Working conventions

- Reports go in `docs/c2/<phase>-REPORT.md` with explicit sections for verified / unverified / failed; failures and aborted runs stay on record, never cherry-picked. Design-doc wording changes are proposed as a separate PR for the owner's review.
- Changes go through PRs into `work`; monsters, models and rendering changes are verified with real screenshots from several angles, not only unit tests.
- Performance policy: do not run A/B comparisons per change; keep hot paths allocation-free (no per-frame strings, boxing, linear scans) and optimise at the end.
