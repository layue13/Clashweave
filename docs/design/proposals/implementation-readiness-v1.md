# 实施前需要补齐的约定

> 用户已接受[综合战斗方案](combat-recommendation-v1.md)作为后续实施基线。当前任务是完善资料并 commit/push，用户审核后再委派原型。本页是技术准备建议，不是已通过的验收结果；补齐候选见[原型说明](prototype-spec-v1.md)。

## 已足够作为实施基线的部分

完整日本刀动作骨架、纳刀重整间合、SA 基础效果与主动变体、气作为临时形态机会、基础防御与有限控制、双视角和服务端权威已有方向。可以用原稿测试值搭建原型，不必先设计完所有武器、SA、形态和最终平衡数值。

用户接受的是综合方案作为基线；原型键位仍需人体工学验证。本次新增 V 主动特殊与 F 临时交互候选以便审核，多个能力装配仍待细化。新的模型格式、导出器和公开接口不因接受总体方案自动成为已验证契约。

## 开始首套运行时前补齐

| 约定 | 需要得到的具体内容 | 推荐处理 |
| --- | --- | --- |
| 首套动作表 | 动作身份、前摇/有效/恢复、位移/转向、成本、命中/格挡/挥空后续 | 按原稿居合、横斩、返刃、重斩、切上、纳刀等逐节点展开，示例参数可调整 |
| 输入与上下文 | 同一节点有哪些玩家选择，分别如何表达，失效请求如何处理 | 补齐主动 SA 和持刀交互入口；配置与动作意图分开，不猜测高成本技能 |
| 状态与提交 | 动作、资源、保护和形态的生命周期 | 成本只在合法动作提交时结算，切物品/GUI 不免费清恢复或保护 |
| 同时攻防 | 同 tick 输入/动作/命中、防御窗口与冲突结算 | 本批候选采用冻结状态、双方独立合法判断、可交换命中、随后统一提交；不靠遍历顺序决定先手 |
| 资源数据最小结构 | 单槽、装配 SA、形态定义、原型参数与持续状态 | 先内部版本化，不过早冻结公开 API；保留未来多能力扩展 |

优先形成可读的节点/边表和一个完整交锋样例，随后实现同一套调度与结算。不把“先补齐”解释成所有动画、数值和远期能力都必须冻结才能写代码。

## 制作正式模型前补齐

使用 Blender，先约定资源尺度、坐标转换、握点/鞘口、刀刃采样标记、网格/纹理及动画导出格式。推荐静态 OBJ＋PNG 起步，动作与简化轨迹采用版本化数据；导出器、加载器和播放器都需实现/验证。

先用粗模完成一次实际客户端导入，检验握持、刀鞘、一次挥刀与方向/尺度，再精修正式美术。身体扭转还需固定共用角色骨架与网格绑定，明确简单部位遮罩/全身覆盖、移动/观察修正、皮肤和盔甲适配；默认单块躯干不能直接表现分段腰胸形变。详细约定见[资源制作模块](../modules/assets.md)。

## 第一次完整可玩验证前补齐

候选键位应支持移动中轻重、防御、回避、纳刀和主动 SA，并能持刀进行必要的原版交互；跳跃/Alt 和持续 Shift 的负担需实际体验。锁敌与鼠标观察的分工应稳定，模式状态与特殊分支有可理解反馈。

用一套完整剑术、具体 SA 样例和临时模式验证继续/终结/收势、普通/精准防御、挑飞/保护及气的一轮循环。普通怪物与不浮空目标也要参与，不能只展示一条训练人偶连段。该样例不限制原稿长期内容范围。

基础阶段同时验证专用服务器不加载客户端类、最小双人同步、切物品/GUI/F5 的状态清理。原仓库构建成功只证明 Forge 骨架工具链；客户端启动、服务端运行、模型导入及战斗尚无本轮验证。

## 推荐实施顺序

1. 展开原稿动作表与输入映射，建立最小数据定义和服务端动作运行时。
2. 并行准备占位刀/鞘与一个挥刀样例，实际验证资源加载、挂点及双视角进度。
3. 接通输入→权威动作→轨迹命中→反馈，早期测试两名玩家与普通实体。
4. 在同一运行时加入防御/崩势/有限追击、SA 变体与气/模式循环，验证完整路线。
5. 调整人体工学和收益关系，再扩充正式动画、特效与内容；第二武器检查框架分工。

文档层面目前不新增战斗代码、Blender 文件或未验证依赖。实施本身的检查随实际变更执行，不用文档检查代替游戏内验证。
