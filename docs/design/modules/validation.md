# 性能、开发阶段与体验验收

> 整理日期：2026-10-08。当前讨论入口；已确认方向与提案分别标明，尚未实现或验证。
> 状态总表：[设计状态](../design-status.md)。原稿章节：[V1.0 设计对照](../archive/v1.0/validation.md)。

## 当前状态

只有 Forge 骨架，既有构建成功记录不代表战斗、动画、网络或玩法通过验收。当前优先整理设计，尚未进入上述功能实现。

本批完善并提交设计供用户审核，审核后才委派原型。具体 P0/P1/P2 交付与复现报告要求见[原型说明](../proposals/prototype-spec-v1.md)，不以阶段先后删减原稿长期内容。

## 设计验收应先明确

用户最新目标是“操作简单、决策博弈、技能好看”。验收建议同时覆盖三者：新玩家能否用少量输入完成基本攻防并体验部分 SA；同样输入是否在不同距离/时机产生值得选择的路线；特效开启时双方是否仍能判断威胁与反击机会。

要检查是否有无脑连点、持续格挡或反复同一 SA 的优势策略，并观察高手优势是否主要来自选择质量。普通动作的表现也需参与体验评估，不能只展示满气终结动画。

完整最小攻击流应包含普通衔接、战术派生、反击、SA 转换与收束，不能只证明左键连击加一个技能按钮可执行。键位方案要支持移动中操作，并覆盖基础攻防。

无爆气时基础战斗与 SA 完整可用；攻击、格挡和受伤都能按规则积攒，慢速武器与受压方不因次数算法明显吃亏。模式必须增加有意义且可应对的选择。

锁敌、弱跟随和自动第三人称需测试手动观察优先、F5、恢复原视角、墙边和目标失效；两视角共享同一动作结果。

## 继承的开发阶段，待重新拆分

基础动作原型 → 双视角表现 → 防御与控制 → SA/模式完整交互 → 第二武器验证 → 多人压力与兼容。原 M1–M7 仅为历史计划，三类 Burst 里程碑不再直接沿用。

原稿将多人压测集中于后期；当前建议基础阶段即验证服务端权威与最小双人同步，后期扩展延迟、低 TPS 和压力测试。

## 验证场景

普通生存、矿洞贴墙、开箱换物品；锁定 1v1 的起手、压制、反击与退出；多人围攻、目标死亡、跨维度与预测拒绝。记录输入是否符合预期、受控时长、模式使用机会、相机覆盖和服务器 tick 成本。

## 操作舒适度验证（建议）

对比原稿左键轻/右键防御/F 重击与最新左键轻/右键重/Shift 防御/Alt 回避布局。覆盖持续向左或右环绕时轻转重、后退格挡、格挡转回避、跳跃后空中回避、频繁纳刀居合、主动 SA 派生与锁敌切换。确认哪些输入需要放开移动键，不能只在站立状态展示连招。

同一套动作图下比较误操作、错过窗口、意外停止移动和玩家报告的手指疲劳；不要用取消权限或招式收益差异替某种布局制造优势。测试不同键盘位置、鼠标中键和无侧键设备，原版潜行/开箱/换物品与 GUI 也要覆盖。当前仅制定验证场景，尚未执行测试。

## 性能边界

20 TPS 世界预算需与既有逻辑共存，动作定义启动时预编译，轨迹只在有效窗检测，网络按事件和必要快照同步。20–50 玩家、50/100/200ms RTT 等原稿目标尚未实测，也未变成当前保证。

旧战斗示例连续花费防御 100 再中立 70 的资源冲突已记录，不作为正确流程示例。后续按已确认模式重新编写逐事件验收流程。

## 原稿细节保留（设计基线，非实现承诺）

以下恢复原稿的具体设计内容，未被明确修改的机制继续作为继承提案，不因整理或精简操作而删除。数值、代码、接口、默认配置及技术断言仍需验证；本模块前文列出的用户调整优先。已调整的键位、单 SA 限制与三类爆气在摘录中改为当前边界，原文仍完整保留。

## 第十八部分：性能目标

20 TPS 下服务器单 tick 目标预算约 50ms。战斗系统必须在这个预算内与原有世界、实体、AI、方块 Tick 共存。

| 项目 | 目标或策略 |
|---|---|
| 服务端逻辑 | 固定 tick，明确阶段顺序 |
| 动作配置 | 启动时预编译，热路径不解析 JSON |
| 命中检测 | 只在有效窗口，AABB 粗筛后窄相 |
| 状态同步 | 事件驱动 + 按需快照 |
| 动画同步 | 不逐帧传输骨骼 |
| 内存分配 | 降低热路径短命对象和 GC 尖峰 |
| 战斗 AI | 非活跃实体不运行完整决策器 |
| 客户端特效 | 对象池、距离裁剪、可调质量 |

“20 名玩家同时战斗仍保持稳定的服务器响应”作为早期目标，但不能预先宣称已经实测达成。测试应关注最慢 Tick、99 分位 Tick、GC 停顿和大规模同时命中峰值。

## 第十九部分：开发计划与验收标准

### Milestone 1：基础操作原型

实现一把打刀、轻攻击、重攻击、格挡、踏步、纳刀、三种攻击、输入缓冲、动作窗口、服务端命中。验收：基础连招可靠、操作结果可预测、挥空与命中可分辨，服务端拒绝非法动作。

### Milestone 2：双视角与动画

完成第一人称武器、第三人称全身动作、F5 中途切换、共享动作时间轴和命中轨迹调试。验收：视角切换不重置动作、不重复伤害，两视角判定一致，正常运动不被夸张动画覆盖。高级越肩镜头可先作为实验模块，不阻塞核心战斗。

### Milestone 3：攻防与崩势

普通格挡、精准格挡、稳定度、崩势、重击破防、训练剑士。验收：持续防御不能无损永久拖延，攻击与防守都能获得合理先机，普通玩家无需连续精准格挡仍可通关。

### Milestone 4：SA

SA 注册、独立/连招/反击变体、次元斩、合法衔接。验收：少量可辨识输入稳定到达多个能力与合法变体，非法请求被拒绝，挥空有成本，SA 可创造新动作路线。

### Milestone 5：Burst

积攒、模式入口、有限规则变化、反馈与服务端同步；具体资源方案未定。验收：辅助基础战斗与 SA，不能刷槽、无限取消或无限浮空。原三类爆气阶段不再直接沿用。

### Milestone 6：第二武器验证框架

实现**长枪**而不是另一把打刀。覆盖另一套射程、轨迹、移动、防御、连招、SA 与 Burst Profile。若核心代码到处增加 `if (weapon == SPEAR)`，说明抽象失败，应该重构接口。

### Milestone 7：多人压测与兼容

测试 20–50 玩家混战、50/100/200ms RTT、抖动、重复/乱序输入、低 TPS、同 Tick 交互、换刀、重生、跨维度及高风险模组兼容。完整记录可重放输入与动作状态。

## 第二十部分：玩家体验验证

### 20.1 三种必测环境

**场景 A——普通生存：** 打僵尸、远程骷髅、矿洞贴墙、攻击后开箱子、切快捷栏和两视角切换。要求不牺牲 Minecraft 基础交互。

**场景 B——剑术 1v1：** 距离、精准格挡、重击破势、SA 派生、双方僵持、合法模式激活与退出。要求多种战术都有适当收益。

**场景 C——多人混战：** 多目标、范围 SA、受压处理、第三人称遮挡和同时命中。要求视觉清楚、服务器结算正确。

### 20.2 推荐体验指标

| 指标 | 用途 |
|---|---|
| 输入到初始动画反馈延迟 | 测量跟手程度 |
| 合法输入实际执行率 | 检查窗口和缓冲 |
| 玩家期望动作与实际动作不一致次数 | 发现上下文选择歧义 |
| SA 使用率 | 判断特殊招式是否融入基础战斗 |
| 模式使用频率与机会 | 检查辅助模式的价值与可用性 |
| 连招平均与最大受控时长 | 发现无限连和控制不合理 |
| 格挡成功率、长时间僵持比例 | 检查防御平衡 |
| 相机遮挡次数与时长 | 评估第三人称可用性 |
| 预测校正次数、幅度、频率 | 评估多人同步 |
| 服务器最慢 Tick、GC | 评估工程性能 |

玩家测试应同时覆盖动作游戏熟练者和普通 Minecraft 玩家。理想结果是前者能利用细节拓展战术，后者不需要读大量手册便能稳定战斗。

## 第二十二部分：V1.0 范围、风险与架构结论

### 22.1 V1.0 与后续版本的边界

| 子系统 | V1.0 | 后续扩展 |
|---|---|---|
| 普通攻击、重攻击、格挡、踏步 | 完整 | 更多方向分支 |
| 居合与打刀连招 | 完整第一套 | 其他剑术流派 |
| Posture 与受控追击 | 基础可玩 | 特殊 Boss 规则 |
| SA | 独立/连招/反击等核心能力 | 更多特殊效果与奥义 |
| Burst | 辅助或模式入口，具体方案重审 | 风格对应的有限变化 |
| 第一、第三人称 | 完整基础支持 | 更高级的动作相机 |
| 自定义骨骼动画 | 数据驱动基础 | 分层混合与高级 IK |
| 联机 | 服务端权威、输入预测 | 有限历史延迟补偿 |
| AI | 测试剑士与训练人偶 | 专用 Boss、复杂战术 |
| 战斗内容 | 打刀；长枪用于框架验收 | 大剑、双刀、拳术、魔法 |
| 扩展 API | 核心注册和声明式规则 | 高级插件机制 |

### 22.2 已知关键风险

1. **1.7.10 全身骨骼动画和旧版渲染兼容。** 应先验证第一/第三人称替换路径，再投入大量动画资产制作。
2. **高级越肩相机与其他核心修改模组冲突。** 必须保证可关闭、可降级，原版 F5 不受影响。
3. **20 TPS 下高速刀刃轨迹。** 需要连续扫掠和合理子采样，不能用单 Tick 静态半径判定代替。
4. **多人 RTT 与精准防御公平性。** 第一版先使规则确定和可预测，再渐进引入有限补偿。
5. **系统复杂度增长。** 打刀是第一套可玩的验证实例，长枪是判断框架抽象是否成功的第二实例。
6. **PvP 控制链过长。** 连招预算、伤害衰减、抗浮空与基础受压保护必须协同测试。

### 22.3 最终架构

```text
                     COMBAT CONTENT
               Weapon / Style / SA / Burst
                            │
                            ▼
                       COMBAT API
                  Registry / Extension
                            │
                            ▼
                       COMBAT CORE
        ┌─────────────────────────────────────┐
        │ Input → Resolver → ActionScheduler  │
        │ ActionGraph / Timeline / State      │
        │ Movement / Collision / Defense      │
        │ Damage / Posture / SA / Burst        │
        └─────────────┬───────────────────────┘
                      │
           ┌──────────┴──────────┐
           ▼                     ▼
    FORGE 1.7.10 ADAPTER    CLIENT PRESENTATION
    Entity / World          First / Third Person
    Damage / Networking     Animation / Camera
    Tick / Lifecycle        Effects / HUD
```

#### 三项原稿技术基线（细节未验证）

1. **统一 ActionRuntime。** 普通攻击、重击、格挡、闪避、SA、Burst 都走一套动作选择、调度、时间轴和结算。
2. **Gameplay 和 Presentation 彻底分离。** 服务端负责规则与战斗结果；客户端负责镜头、动画和特效，两种视角只是表现适配器。
3. **Combat Style 组合式扩展。** 新武器组合动作图、输入配置、资源、运动、防御与特殊能力，而不是在核心中不断写武器特判。

#### 结语

Clashweave 的目标不是“特效更华丽的 SlashBlade”，而是建立一套能在 Minecraft 1.7.10 上长期复用的动作战斗基础设施。**操作简单、决策深刻、联机可信、视角自由、内容可扩展**，才是这套框架真正的产品价值。

> **版本说明：** 本文为可进入原型开发的 V1.0 设计基线。上述战斗帧数、资源消耗、判定角度、镜头距离和网络缓冲等均为初始测试参数，需经真实玩家和多人联机测试后确定，不应被视作已验证的最终平衡。本文中的 Java、JSON、INI 示例用于表达接口与数据形态，未保证直接在 Forge 1.7.10 下编译运行。
