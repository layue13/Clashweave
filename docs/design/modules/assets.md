# 刀模型、动画与资源制作

> 战斗总体方案已由用户接受作为实施基线。本页回答实施准备与 Blender 制作问题，资源格式和导出流程是新的技术推荐，尚未实现或验证。
> 相关模块：[视角与表现](presentation.md)、[命中与运动](collision.md)、[实施准备](../proposals/implementation-readiness-v1.md)。

## 工具推荐

推荐 Blender 作为主工具，制作刀/刀鞘、UV、贴图烘焙、角色/手臂骨骼动画与轨迹采样。Blockbench 可用于偏 Minecraft 方块风格的静态模型或快速占位，但不是必须经过的步骤。固定一个项目使用的 Blender 版本，随源文件记录版本；目前不指定未经本项目验证的插件或运行时库。

刀通常作为刚性模型随握点运动，不需要为了普通挥刀给刀刃做蒙皮。手臂/角色骨骼决定握持动作，刀鞘独立挂在身体节点上。确有弯曲、展开或变形的特殊武器，再声明额外骨骼或模型切换。

## 首个资产的组成

| 资源 | 建议内容 | 用途 |
| --- | --- | --- |
| 刀模型 | 刀身、刀镡、刀柄的低面数刚性几何与 UV | 两视角共用武器几何 |
| 刀鞘模型 | 与刀分开的刚性几何 | 腰间挂载、拔刀/纳刀时的状态展示 |
| 贴图 | PNG，先使用简单颜色/纹理 | 检验 UV 和游戏中轮廓，不依赖完整材质系统 |
| 握点与标记 | 刀的握点、刀刃基部/中部/刀尖，刀鞘鞘口 | 挂载、刀光、简化轨迹导出 |
| 动画源 | 第一人称手臂与第三人称角色的样例动作 | 同一动作身份的两套表现 |
| 逻辑轨迹 | 动作局部空间中的刀刃采样和期望位移 | 服务端命中和真实运动求解 |

刀光、粒子、空间斩和镜头反馈由游戏的表现系统生成，不需要全部烘成刀模型几何。普通攻击也要在关闭强光特效后保持可读。

## 玩家身体扭转与角色骨架（技术推荐，待验证）

建议在 Blender 中建立项目共用的 Minecraft 比例角色骨架，为腰/胸转动、肩部发力、挥刀与重心制作动作。刀刚性挂在手部节点，刀鞘挂在骨盆/腰部节点；胸口转动时肩膀、手臂、握点和刀继承对应变换，不能只旋转躯干几何而让手和武器停在原处。

```text
root（角色局部基准）
└─ hips（骨盆）
   ├─ 腿部节点
   └─ spine（腰/脊柱）
      └─ chest（胸）
         ├─ neck / head
         ├─ 左肩 → 上臂 → 前臂 → 手
         └─ 右肩 → 上臂 → 前臂 → 手 → grip → 刀

hips → sheath_mount → 刀鞘
```

此树说明层级，不冻结最终骨骼数量。默认 Minecraft 躯干是一个刚性方块，只转它可以获得整体上身旋转，但无法表现胸腰分段扭转；手臂也需分段或蒙皮才能表现肘部弯曲。ModelBiped 可作为占位/兼容适配路径，正式表现建议使用保持方块轮廓和玩家皮肤映射的分段角色网格，或明确的轻量蒙皮方案。不能只增加骨骼、不绑定对应几何，就期望身体产生新形变。

### Blender 中如何制作

固定绑定姿态、骨骼层级和局部轴。先制作一段横斩：准备阶段胸肩回转，出刀时胸肩与手臂协同，恢复阶段回到可衔接姿态；骨盆/脚是否参与按动作的位移和稳定性决定。不能把“先转腰后动手”当作所有招式都必须遵守的真实剑术规律，具体动作看轮廓、节奏和攻击轨迹。

骨架可在 Blender 使用 IK、约束和控制器帮助摆姿势，导出时把结果烘焙为项目需要的骨骼局部变换曲线。游戏不需要自动支持 Blender 的全部控制器。作者制作时的 IK 与运行时脚底贴地/双手校正 IK 是不同功能；高级运行时 IK 可按原稿规划后置。

### 游戏中如何与移动和观察组合

| 动作来源 | 推荐影响部位 | 组合边界 |
| --- | --- | --- |
| 站立/移动 | 基础全身姿态，重点是下肢 | 允许移动的上身攻击可保留走路；不能把冲刺重斩硬叠成站立挥刀 |
| 普通攻击/格挡 | 声明的腰胸、肩臂与必要头部姿态 | 原型先用简单部位遮罩与过渡，不让原版走路覆盖正在挥刀的手臂 |
| 居合、重斩、空中或特殊动作 | 动作声明的全身范围 | 需要时取得腿部/骨盆表现控制，但真实位移仍由 Gameplay 决定 |
| 观察/锁敌修正 | 有界头部和部分上身修正 | 鼠标观察优先；攻击承诺阶段不因转镜头把刀轨迹任意旋转 |
| 受击、崩势 | 被规则中断或覆盖的姿态 | 与权威动作结果一致，结束后按定义回到合法状态 |

动作播放器在客户端按同一动作进度采样骨骼，转换时做短过渡；旋转可使用四元数插值，避免直接线性混合欧拉角造成大幅绕转。部位遮罩、覆盖和少量修正的优先级应明确；复杂多层叠加不作为首个管线样例前提。

第一轮先用固定几何比例和一段攻击验证，再加入移动叠加、头部观察和受击优先级。预备动作/恢复的可读性优先于无限制的扭转幅度；角度限制结合角色几何、镜头与攻击方向测试，不先写成普遍固定值。

### 命中、同步与兼容

表现骨骼跟随已定义的动作和攻击朝向，镜头/头部观察不独立扩大命中范围。刀的可见轨迹应与权威轨迹对齐；客户端细节修正不直接修改服务端判定。角色起手转向、招式位移与扭转表现分别声明。

网络发送动作实例、开始时间和必要方向/状态，由远端播放器采样，不逐帧发送全套骨骼。第一人称另用手臂/刀的近景表现，不把第三人称扭腰强行变成镜头摇晃。

玩家皮肤、盔甲、披风、其他持物和玩家模型替换都需随骨架或适配器检查。不能假定第三方盔甲会自动适配分段躯干；不兼容时使用既定简化路径，保留战斗结算。持有受支持武器时按内容规则启用动画，不无条件更换所有玩家的全局外观。

## 建议的最小导出约定

原稿规划了自定义骨骼与 Gameplay/Presentation 分离。首轮推荐采用易于验证的文件分工，而非宣称 Minecraft 原生支持所有 Blender 资源：

```text
Blender 源文件 .blend
  ├─ 刀 / 刀鞘静态几何 → OBJ
  ├─ 简单颜色贴图 → PNG
  ├─ 挂点和动作表现 → 版本化 JSON（需实现导出器与播放器）
  └─ 刀刃轨迹 / 期望位移 → 独立 Gameplay JSON（需采样与校验）
```

OBJ 只作为静态几何的起点，不承担骨骼或动画。本项目尚无对应模型接入；需在 Forge 1.7.10 实际客户端中验证加载器、纹理路径、法线、透明和渲染状态。不能把 .blend 放进资源包就认为游戏能播放动作。若未来考虑 glTF 等格式，应先验证 Java 8/1.7.10 的加载与渲染路径，再调整导出约定。

第一版材质以颜色贴图为主；Blender 的灯光、程序节点或完整 PBR 材质不会自动变成游戏运行时效果。需要的外观先烘焙到贴图，额外光照/发光表现单独实现和验证。

## 建模前约定的尺度、原点与命名

建议资源单位按 1 单位 = 1 Minecraft 方块约定，在 Blender 中放置与游戏角色比例一致的参考体。最终刀长由角色握持和战斗轨迹验证，不照搬软件中任意缩放；ModelBiped 等适配器的内部单位由适配层显式换算。

刀对象以握点作为原点，长轴与刀尖方向统一约定；刀鞘以鞘口作对齐参考。建议标记命名为 `grip`、`blade_base`、`blade_mid`、`blade_tip`、`saya_mouth`，角色侧另有手部与腰间挂点，避免把它们混在同一个空间。

Blender 默认 Z 向上，游戏侧 Y 向上，导出时需要一致的坐标转换。模型、挂点、骨骼、轨迹和 Root Motion 必须使用同一变换；首次测试同时检查前向、左右、绕轴旋转、面朝向和法线，不能只凭模型静止时看起来朝向正确就验收。

输出网格应应用对象尺度等已声明的变换，使用确定的三角化结果，检查法线、UV 和镜像变换。带骨骼的资源按固定绑定姿态导出，不要求作者随意在动画制作后修改骨架或应用破坏绑定的变换。具体操作由版本化导出器校验和执行。

源资源与游戏资源分开保存：`.blend` 和纹理源文件作为可编辑资料；运行时只打包导出的几何、贴图和声明数据。具体目录及格式版本在首个导入样例中建立，不将源文件路径硬编码成资源身份。

## 首个导出样例的数据契约（审核候选）

| 数据 | 必须携带的信息 | 运行侧 |
| --- | --- | --- |
| 资源清单 | 格式版本、资源身份、单位/坐标约定、几何/贴图/骨架/动作引用 | 客户端编译校验；逻辑资源另有独立清单 |
| 骨架 | 稳定节点名、父节点、绑定姿态及局部变换；挂点归属 | 客户端，第一/第三人称明确各自绑定 |
| 动画片段 | 动作身份、持续时间、秒为时间基准的关键帧、位置/旋转/缩放、插值方式 | 客户端按权威动作进度采样 |
| 动作覆盖 | 身体部位遮罩/全身覆盖、转换规则、与观察修正的优先关系 | 客户端，不单独变更命中 |
| Gameplay 动作 | 前摇/有效/恢复、左闭右开窗口、成本/转换条件、局部轨迹/期望位移 | 服务端权威，客户端可用于预测/调试 |
| 来源记录 | Blender 版本、导出器版本和源文件身份 | 制作追踪，不把本机绝对路径打入游戏资源 |

首轮旋转推荐四元数曲线，骨骼父子关系和坐标转换统一。缺失引用、重复节点、循环父子关系、非法窗口、非有限数值与不支持版本应在加载时明确拒绝；不能悄悄播放错误模型或以零成本动作继续运行。具体 JSON 字段/API 由首个样例验证后稳定，不因本表提前冻结公开接口。

## 动画、时间与碰撞的关系

第一人称重点是手臂、武器和目标可见性，第三人称重点是全身姿态与空间位置。两者共享动作 ID、进度和服务端结果，可以使用不同表现曲线；不用一套全身动画强行承担所有近景镜头，也不因 F5 切换重启动作。

Blender 时间按秒或帧制作，导出器需记录时间基准并转换。Gameplay 窗口沿用原稿 tick 与左闭右开约定，渲染按动作进度插值；不能把 Blender 第 5 帧直接当成 Minecraft 第 5 tick。

服务端只加载简化的权威轨迹和期望位移，不加载视觉网格、骨骼播放器或 OpenGL。碰撞轨迹可以从指定的权威动作源中采样，但必须独立校验；第一人称视觉夸张不改变它。真实位移经世界碰撞求解，动画 Root Motion 不直接穿墙移动角色。

## 先验证什么

[S4 实测](../../probes/S4-rendering.md)已在 Blender 5.2.2 LTS 和实际 Forge 客户端完成静态 OBJ/PNG、刚性手/腰挂点与同实例视角进度验证。限定为原版 ModelBiped 适配，分段躯干、骨骼、轨迹对齐和其它模型兼容均未验收。

第一轮使用占位刀与刀鞘，验证尺度、挂点、纳刀态显示、手持显示及一段横斩的刀尖轨迹。随后接入第一/第三人称表现和 F5 中途切换，再逐步制作居合、返刃、重斩、格挡、纳刀与追击。完整原稿内容保留，这个顺序仅降低管线返工。

验收包含：游戏内与 Blender 的尺度/方向一致；刀不会握反或沿错误轴旋转；刀鞘状态可切换；动画和有效窗口可对齐；躯干扭转时肩臂/刀正确跟随；移动/观察不覆盖动作承诺；服务端能独立加载轨迹；模型/动画修改不会重复命中；材质与渲染状态不污染其他物品或玩家。
